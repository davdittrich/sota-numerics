A blocking plan:post gate checks the section structure below. Consulting the sources and judging the comparison stay with you; no gate checks them.
For every non-trivial mechanism or library choice, name at least 2 current alternatives, each carrying a source you actually consulted — a URL or a backticked doc-ref — and a 4-digit year, and state which criterion decided the pick, ranked in this order: performance, simplicity (including lines of code), ecosystem support, maintenance overhead.
Write the section as a `## Alternatives Considered` heading followed by bold-named mechanism alternatives, as either bullets (`- **Name**: ...`) or framed Markdown table rows, and close it with a `Decided by:` line naming the winning criterion.
Put project-local reasoning under the exact heading `### Internal design alternatives`, in the same entry shapes, until a peer level-three heading ends it. Internal entries need no external citation or date, do not count toward the two mechanism alternatives, and cannot lend evidence to a mechanism entry.
A plan that is pure config, documentation, or a mechanical rename with no real mechanism choice may write `N/A — no mechanism choice` as the entire section body instead of fabricating a comparison.
A phase that already has a SPEC.md still requires this section in PLAN.md: SPEC.md locks what is built, this section documents how the mechanism was chosen, and the gate checks PLAN.md, not SPEC.md.
An entry passes the date check when at least one of its cited years falls inside the six-year window. So pair a canonical source (Kahan summation, IEEE 754, a classic BLAS paper) with a current doc, release note, or benchmark that supplies an in-window year.
List a third alternative when the choice is genuinely close.
A plan goes with the grain when the code it asks for matches the conventions already in the project — its naming, its error shape, its module layout, its test placement — so a reader cannot tell from the code which file is new.
Give every task a bound the executor can check from the repository or a command's output, so "done" needs no question to the author.
