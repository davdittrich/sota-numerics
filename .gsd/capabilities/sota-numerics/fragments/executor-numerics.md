Numerical-stability and efficiency discipline for execution is advisory only — this capability's single gate already fired at plan:post, not here.
Derive numeric parameters (tolerances, iteration counts, thresholds, learning rates) from first principles or the problem's actual scale, not by tuning a value until a test happens to pass.
Prefer numerically stable formulations over merely convenient ones — reformulate to avoid catastrophic cancellation (subtracting nearly-equal large quantities) and avoid letting rounding error propagate silently through a chain of operations.
Where efficiency and simplicity conflict, favor efficiency and speed, per this project's own priority order, and treat the emitted code as complete and unambiguous at the point of use: every branch the caller can reach is written, every argument the code accepts has a defined meaning, and a value the caller must supply is named rather than defaulted silently.
If a simplification trades away precision, label it with its ceiling (the condition under which it breaks) rather than leaving it silent — a `# ponytail:`-style comment naming the ceiling is the right shape.
Code an agent runs directly by hand — a script, a CLI, a test harness, or a hook — is **quiet**: on success it prints a compact machine-readable result or nothing at all, on failure it prints one line naming the problem and one line naming the fix, it signals through its exit code with no progress chatter, and when a result is large enough to flood the context window it writes the result to a file and prints that file's path.
This capability's own gate script demonstrates the shape: it prints `<plan_path>: <reason>` for each violation followed by exactly one `remediation: ...` line, and gsd-tools shows the same restraint at larger scale by swapping stdout for an `@file:<tmp>` pointer once a result exceeds 50000 bytes.
This rule governs scripts, CLIs, test harnesses, and hooks an agent invokes; library internals an agent never runs by hand are outside it.
Agent-facing prose is **legible** when it is unambiguous and complete: keep each meaning in exactly one place so a comment states why and the code states what, and delete any line the reader would already honor by default.
Phrase every instruction as the target behavior, give every completion criterion a bound the reader can check, and keep a definition next to the caveats that qualify it.
The same ceiling rule applies here: name the ceiling of any simplification in the prose itself, not just in the code.
